# ADR-004: permission reply via serve HTTP

Date: 2026-10-02. Status: accepted (spike-verified live on opencode 1.18.32).

Context: Neko UI must answer OpenCode permission requests. The plugin is
push-only (no inbound channel), so the reply must originate from Neko Core.

Decision: Rust Core POSTs directly to the OpenCode serve HTTP API:

- `POST {serve}/permission/{requestID}/reply` with
  `{"reply": "once" | "always" | "reject"}` (verified: 200 `true` unblocks
  the agent; unknown id yields 404 `PermissionNotFoundError`).
- `GET {serve}/permission` lists pending (verified shape:
  `{id, sessionID, permission, patterns, metadata, always, tool}`).
- The plugin forwards `id` as `payload.requestId` in `permission.requested`
  (upstream `tool` is an object `{messageID, callID}`, not a name — the
  `permission` field already names the tool).
- Serve address comes from `NEKO_OPENCODE_URL` (e.g.
  `http://127.0.0.1:18789`). No port scanning, no client-internals scraping.
- Reply requires `opencode serve`/`web` running. TUI-only sessions stay
  observe-only with an explicit notice in the UI.

Consequences:

- New failure mode: serve unreachable → bubble shows error, agent keeps
  waiting (never auto-approved, never auto-rejected).
- `message` field always omitted in MVP replies.
- If upstream changes the route, this ADR must be revisited with a new spike.
